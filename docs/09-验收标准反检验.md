# 09 · 验收标准反检验（Adversarial Review）

> **历史文档**：本文件为反检验过程产物，其补丁已被 docs/06（权威全集）超集取代并扩展。阅读本文件可了解补丁来源，权威 AC 以 docs/06 为准。

## 方法

给每条关键验收标准构造一个**真实作弊/失败场景**，检验它能不能拦住要防的坏事：
- 🟢 **通过**——按当前条文即可拦住
- 🟡 **有漏洞**——核心有效，但存在可绕过的边界，需打补丁
- 🔴 **失守**——条文挡不住，必须重写

> 反检验的价值不在"确认 AC 没问题"，而在**找到漏洞**。下面 8 条都攻了一遍。

---

## 一、逐条反检验

### 🟡 AC-DM-01 · 决策卡必填项缺一不可创建
- **要拦的**：模糊问题、无选项、无责任人、无截止的"决策"。
- **攻击场景**：PM 为了过创建校验，填两个**内容相同**的选项（"方案一:上线 / 方案二:上线"）；决策人填**自己**；截止时间填**过去**或**极远**。
- **漏洞**：条文只校验"有 ≥2 选项 / 有唯一决策人 / 有截止"，**不校验选项是否互斥、决策人是否自决、日期是否合理**。
- **补丁**：
  - → **AC-DM-01a（新）**：选项须**结构化互斥**——每个选项必须声明不同的「上线时间/成本/范围」取向，两选项取向完全相同则拒绝。
  - → **AC-DM-01b（新）**：影响等级达阈值时，**决策人 ≠ 提出人**；截止时间须 ≥ 当前且 ≤ 所阻塞里程碑日期。

### 🟡 AC-DM-07 · 关闭前置须有落地动作并被确认
- **要拦的**：决策"已决"但不落地、飘在空中。
- **攻击场景 A**：PM 建一个**空壳任务**当落地动作，自己点"确认关闭"，决策随即关闭——闭环是假的。
- **攻击场景 B**：PM 干脆用**「已撤销」**绕过关闭门槛，撤销理由写"已处理"——撤销成了逃生通道。
- **漏洞**：A——落地动作只要"存在+被确认"，**不要求质量、不要求回链、确认人可自审**。B——撤销不校验理由真实性，可滥用逃逸闭环纪律。
- **补丁**：
  - → **AC-DM-07a（强化）**：落地动作须达**「已执行/已关闭」**（非草拟），且**类型须与所选选项一致**，并**回链该决策**。
  - → **AC-DM-07b（新）**：落地动作的**确认人须为动作责任人或决策人**，提出人不得自确认。
  - → **AC-DM-07c（新）**：撤销理由**结构化**；「已实际执行」**不是合法撤销理由**（这类应走 已决→已执行→关闭）；项目/团队**撤销率超阈值自动告警**。

### 🔴 AC-DM-12 · 阻塞里程碑的决策逾期 → 否决 → 红
- **要拦的**：关键决策拖着不放，把交付拖死。
- **攻击场景 A**：PM **从不把决策关联到里程碑**（关联对象填了别的），系统不知道它阻塞谁 → 否决永不触发。
- **攻击场景 B**：PM 把决策截止日设到**很远的未来**，永远不会"逾期" → 升级和否决都不触发。
- **漏洞**：A——阻塞关系靠人声明，漏填即失效。B——截止时间不受"所阻塞里程碑"约束，可无限推迟。
- **补丁**：
  - → **AC-DM-12a（强化）**：阻塞关系须**声明或自动探测**——当某关键路径任务标记"等待决策 X"时，系统自动建立阻塞关系，即使 PM 未关联。
  - → **AC-DM-12b（新）**：决策**截止时间须 ≤ 所阻塞里程碑日期**（或 ≤ 里程碑 − 缓冲），否则拒绝或强提示。

### 🟡 AC-DM-13 · 升级系统自动执行，不依赖 PM 手动催办
- **要拦的**：靠人催的"自动化"=没有自动化。
- **攻击场景 A**：决策人在组织结构里**没有上级**记录 → 升级无目标 → 自动化静默失败或只记日志。
- **攻击场景 B**：决策逾期后，PM **反复编辑截止时间**，每次重置计时 → 永远到不了"逾期/升级"。
- **漏洞**：A——升级链依赖未保证存在的组织数据。B——改期可重置升级时钟。
- **补丁**：
  - → **AC-DM-13a（新）**：升级目标须**可解析**；解析失败**默认升级到 PMO/发起人**并标记"升级目标缺失"；**逾期或过半后，截止时间编辑受限**且审计留痕，逾期状态**粘滞**——改期不重置决策债计息时钟。

### 🟡 AC-HS-06 · 命中否决强制红，即使合分 ≥ 80
- **要拦的**：总体好看但存在致命单点时的"假绿"。
- **攻击场景 A**：否决项"关键路径已滑移"依赖**关键路径计算+基线**——MVP 轻版可能不算 CPM → 该否决**静默永不触发** → 项目一路绿。
- **攻击场景 B**：PM 上传**一行文字恢复方案**（"恢复:加班"）→ 否决解除 → 状态回黄/绿，实际问题没修。
- **漏洞**：A——否决依赖未必存在的数据，缺失时静默放行而非提示。B——"恢复方案"是自由文本，无质量门槛。
- **补丁**：
  - → **AC-HS-06a（强化）**：恢复方案须为**带责任人+截止的可追踪行动项**，非自由文本；行动项进入"进行中/已关闭"前，否决**不解除**。
  - → **AC-HS-06b（新）**：各否决项**按阶段标注是否启用**；缺数据的否决须显示**「未启用(缺数据)」**，**不得静默放行绿**。

### 🟡 AC-HS-07 · 否决消除后按分重新定级，不可红直接跳绿
- **要拦的**：否决一解除就假装没事直接绿。
- **攻击场景**：利用 AC-HS-06 的 B 漏洞，用假恢复方案解除否决 → 状态"合规地"跳回 → 实质绕过了本条。
- **漏洞**：本条**完整有效**，但其完整性**依赖 AC-HS-06a**。AC-HS-06 不加固，本条形同虚设。
- **补丁**：不另立新条，**强化 AC-HS-06a 即同时修复本条**。标注：AC-HS-07 ∥ 依赖 AC-HS-06a。

### 🟡 AC-HS-18 · 绿→黄：PM 24h 内提交纠偏方案
- **要拦的**：变黄了不被认真对待。
- **攻击场景**：PM 提交**一行文字**（"会赶进度"）→ 满足"已提交"→ 不触发升级发起人。
- **漏洞**："提交"校验存在性，不校验实质。
- **补丁**：
  - → **AC-HS-18a（强化）**：纠偏/恢复方案须含**可追踪行动项（owner+deadline）**；纯文本不解除告警。

### 🔴 AC-HS-04 · 缺数据维度不计入合分，标注"数据不全"
- **要拦的**：维度无数据时分数不假高。
- **攻击场景**：项目早期，8 维里 6 维无数据 → 只有 2 维贡献 → 合分可能显示 **85（绿）**，旁边小字"数据不全"。高管扫一眼只看到绿。
- **漏洞**："数据不全"只是**标注**，**不改变灯色**——一个几乎没数据的项目仍可显示令人放心的绿。
- **补丁**：
  - → **AC-HS-04a（强化）**：有效数据维度数 < 阈值（如 < 4）时，项目**不得显示为绿**，显示为**「灰 · 评估中」**；数据齐全后才进入正常红黄绿。

## 二、共性漏洞（一条原则修复一半问题）

8 条里 6 条的根因是同一个：

> **验收标准检查了"有没有"，没检查"是不是真的"——自由文本、自审确认、可改期的截止，是三大逃生通道。**

由此提炼一条横切原则，应作为所有"提交/确认/方案"类 AC 的共同前置：

> **原则 AC-X01（新）**：凡"提交方案 / 确认闭环 / 解除告警"类动作，**必须产出可追踪对象（行动项/落地动作，带责任人+截止）**，不接受纯自由文本；可追踪对象须有独立确认人，且其状态变更留痕、可回溯。

落实这条，AC-DM-07a、AC-HS-06a、AC-HS-18a 自动生效大半。

## 四、结论与裁决

- **2 条失守**（🔴 AC-DM-12、AC-HS-04）：原文挡不住，**必须按补丁重写后再进 PRD**。
- **6 条有漏洞**（🟡）：核心有效，**补丁后可放行**。
- **1 条横切原则**（AC-X01）一次性收紧多处软肋。
- 反检验后，**06 验收清单需追加 13 条**（上表），并在 MVP 范围内优先落实失守的 2 条及其依赖（AC-DM-12a/b、AC-HS-04a）。

> 一句话：这批验收标准的骨架是好的，但**普遍缺"反作弊"层**——补丁全部围绕"把自由文本和自审确认换成可追踪对象"这一件事。这是从"看着专业"到"真的拦得住"的最后一公里。
