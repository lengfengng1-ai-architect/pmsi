# 01 · 产品定位与设计框架

## 一、设计定位与目标用户

市面上大多数工具停留在「任务跟踪 + 看板」，PMP 里最值钱的能力——范围分解、成本预算、风险与变更控制、相关方对齐、价值度量——反而没人做好。本系统的差异化押在这里。

| 维度 | 定位 |
|------|------|
| **核心主张** | 战略→组合→项目→交付，一条线看穿（Line of Sight） |
| **目标用户** | 项目型组织、研发/咨询/工程类企业、PMO、项目经理、业务负责人 |
| **要解决的真问题** | 项目「做了不少、价值看不到」；范围蔓延无控制；成本失控；风险事后救火；知识不沉淀 |
| **不做的事** | 不做即时通讯、不做代码托管、不做财务总账——专注项目经营，靠集成而非替代 |

## 二、文章核心框架：拆、控、推、追、回

顶级 PM 不是更能熬、更能催，而是做事方式不同——一套固定管理动作：

| 字 | 一句话 | 普通 PM | 顶级 PM |
|----|--------|--------|--------|
| **拆** | 接任务前先拆 | 直接领活儿 | 拆目标/范围/任务/责任/节点/交付物 |
| **控** | 提前控风险而非事后救火 | 等问题爆了才处理 | 把每次「问题不大」都拦住 |
| **推** | 推动关键人做决策，而非传话 | 当传声筒 | 把模糊问题变成「选择题+截止时间」 |
| **追** | 追到真正闭环，而非提醒 | 「推进一下」「差不多了」就放过 | 追交付物、追确认结果、追关闭 |
| **回** | 项目结束一定复盘回收经验 | 散场冲下一个 | 把经验变成模板/清单/规则/预警项 |

**关键结论**：项目多了，靠人脑记必然回到「天天催天天问」的低效状态。系统价值不是多填表，而是把「拆控推追回」固化成组织能力。

## 三、设计原点

> **这个系统存在的全部理由，就是让一个普通团队，被迫（并逐渐习惯）用顶级 PM 的方式做事——拆得清、控得早、推得动、追得闭环、回得有沉淀。**

于是系统有两层骨架：
- **明线**：拆、控、推、追、回（用户感知）
- **暗线**：PMP 十大知识领域（内在严谨）

## 四、三层业务架构

```
┌─────────────────────────────────────────────┐
│  组合层 Portfolio  — 战略对齐、投资排序、容量   │   ← 管项目该不该立项
├─────────────────────────────────────────────┤
│  项目层 Project     — 范围/进度/成本/风险/质量 │   ← 管项目怎么做对
├─────────────────────────────────────────────┤
│  执行层 Delivery    — 工作包/任务/迭代/交付物   │   ← 管活儿怎么做完
└─────────────────────────────────────────────┘
         ↕ 三层之间靠「度量」与「变更」贯通
```

- **上层**决定做不做（ROI/战略契合度）
- **中层**决定怎么做（铁三角：范围-进度-成本）
- **下层**决定做得动不动（工时/交付物）

## 五、PMP 全生命周期（五大过程组）

| 过程组 | 系统里的业务动作 | 核心产物 |
|-------|---------------|--------|
| ① 启动 | 立项申请→商业论证→章程→任命 PM→识别相关方 | 项目章程、相关方登记册 |
| ② 规划 | 拆 WBS→排进度→编预算→配资源→登记风险→建基线 | 计划 + 基线 |
| ③ 执行 | 分配任务→记录工时→产出交付物→沟通→采购 | 交付物、绩效数据 |
| ④ 监控 | 挣值分析、偏差预警、风险燃尽、变更审批 | 绩效报告、变更状态 |
| ⑤ 收尾 | 验收→经验教训→归档→收益跟踪 | 结项报告、知识库 |

**设计原则**：监控贯穿执行全程，系统默认对 CPI/SPI 设阈值触发预警——把「靠感觉判断」变成「靠数据报警」。

## 六、适配多种开发模式（Tailoring）

支持三套并存的项目运行模式，按项目类型自动裁剪流程开关：

| 模式 | 适用 | 表现形态 |
|------|------|---------|
| 预测型（瀑布） | 需求明确、变更代价高 | 强基线、重变更控制、甘特为主 |
| 适应型（敏捷） | 需求不确定、快速验证 | 迭代/看板、燃尽图、轻基线、故事点 |
| 混合型 | 大多数真实项目 | 上层预测管范围/预算，下层敏捷管交付 |
